# Tabu + Clique-Guided Worker

> **Retired 2026-05-06.** A 48-hour, 4-worker A/B run produced 0 improvements across 1,351 completed trajectories (~6.75M iterations, 6,755 diversification cycles). Same end-state as VDS. Compose service remains defined at `scale: 0`; code is left in place for any future re-run under a different move shape or candidate-generation policy. Full retirement record: [`docs/investigations/retired-trajectory-methods.md`](../investigations/retired-trajectory-methods.md) (original investigation doc in git history). This doc is preserved as the algorithmic reference for that future re-run.

## Overview

The tabu worker walks a long sequential trajectory through the graph state space, picking the best balanced edge-pair flip at each step from a candidate pool generated by clique-guided sampling, and using edge-level memory ("tabu") to prevent immediate oscillation. The combination is the most empirically validated heuristic-search technique for Ramsey lower bounds at n > 100 — Exoo's tabu search established R(3,13)≥59, R(4,10)≥80, R(4,11)≥96, R(4,12)≥106, R(4,13)≥118, R(4,14)≥129, R(5,8)≥95. The empirical finding from our A/B run is that those wins do not transfer to n=282 at ~790K cliques with our balanced-pair move shape.

Tabu was investigated in `docs/investigations/retired-trajectory-methods.md` (consolidated; original in git history). It was the next algorithmic build after VDS retirement; it has now followed VDS into retirement. Worker code lives in `src/tabu.rs` and is wired through `cycle_tabu_search` in `src/worker.rs`.

## High-Level Strategy

Each tabu run executes a complete trajectory starting from the current stage's base graph:

1. Build the base graph and `CliqueCollection` from the stage config.
2. Compute the initial monochromatic clique count via `get_cliques_comprehensive`.
3. Pre-sort static high-participation edge pools (one per color), sorted descending by clique-participation score.
4. For each iteration up to `max_iterations`:
   - Generate red-candidate and blue-candidate pools (clique-seeded + top-participation, filtered by tabu).
   - Score every (red, blue) pair via incremental delta evaluation. Pick the minimum-delta pair.
   - Apply the move; update tabu lists and destroyed-clique tracking.
   - If the new state beats the global best, update best and reset adaptive tenure to base.
   - If the new state beats the Redis top-N threshold, mark as improvement to submit.
   - If `iter_since_improvement` exceeds `restart_after`, diversify (random balanced perturbation), clear tabu and destroyed sets.
5. After the budget exhausts, submit the best graph as a full bitstring (long trajectories may walk far from base, so edge-flip lists would be unwieldy).

### Move Shape: Balanced Pairs, Not Single Edges

Exoo's papers operate on single-edge flips because they search for graphs with 0 cliques (where edge balance is unconstrained). Our problem requires balanced graphs (|red − blue| ∈ {0, 1}), so each tabu move flips one currently-red edge and one currently-blue edge simultaneously, preserving parity. This matches the exhaustive engine's work-unit shape and is a deliberate divergence from the literature noted in the investigation doc.

### Candidate Generation: Clique-Guided + Top-Participation

Per iteration, two pools are built (one red, one blue):

1. **Seed from a randomly sampled surviving k-clique.** Pick a random clique index, skip if it has been marked destroyed, otherwise add all `(k choose 2)` of its edges to the appropriate-color pool. These are guaranteed-impactful: flipping any one breaks at least this clique.
2. **Top up from pre-sorted high-participation pools.** Each color has a list of all currently-colored edges sorted descending by clique participation. Add edges in order until the pool reaches `candidate_pool_size`.
3. **Filter by tabu.** Edges currently in the tabu list (within tenure) are skipped.
4. **Truncate** each pool to `candidate_pool_size` (the seed step may over-fill).

The pre-sorted pools are computed once at run start from the static `CliqueCollection`. Their accuracy degrades over the trajectory as moves change which edges participate in surviving cliques, but periodic diversification gives a natural quality-reset point and keeps staleness bounded.

### Move Scoring: Incremental Delta via Edge-Seeded Bron-Kerbosch

This is the dominant per-iteration cost. Each candidate pair is evaluated via:

```rust
fn evaluate_pair_delta(graph, clique_size, red, blue) -> i32 {
    let edges = [red.clone(), blue.clone()];
    let destroyed = get_new_cliques(graph, clique_size, &edges); // pre-flip
    graph.flip_edges(&edges);
    let created = get_new_cliques(graph, clique_size, &edges);   // post-flip
    graph.flip_edges(&edges);                                    // restore
    created - destroyed
}
```

`get_new_cliques` is the same edge-seeded Bron-Kerbosch the exhaustive engine uses for delta evaluation. It counts only monochromatic cliques containing the flipped edges — pre-flip call gives destroyed cliques (cliques currently containing those edges in their current color), post-flip call gives created cliques (cliques in the new graph containing those edges in their new flipped color). Exact delta, no dependency on the static `CliqueCollection`, no staleness issue regardless of trajectory length.

A unit test (`evaluate_pair_delta_matches_full_recount`) verifies this incremental delta exactly equals `(post_flip_count − pre_flip_count)` from a full recount.

### Tabu Memory and Adaptive Tenure

Two `HashMap<(u16, u16), u64>` lists (one per color) map ordered edges to their expiry iteration. Lookup is O(1); pruning is amortized — every 256 iterations the list is swept to drop expired entries.

Tenure is adaptive:
- Base: `base_tabu_tenure` (~`sqrt(num_edges)` ≈ 200 for our 39,621-edge graph)
- Widens by 10% every 500 iterations without improvement, capped at `max_tabu_tenure`
- Resets to base on any improvement

This biases the search to escape stuck regions by progressively forbidding revisits, then loosens once it finds improvement.

### Aspiration

Aspiration is implicit in this implementation: an improvement that beats the global best is always recorded (and submitted to top-N if it beats the Redis threshold) regardless of any per-move tabu signal — because tabu filtering happens at *candidate generation*, and the move-scoring step applies to whatever candidates make it through. If a tabu edge would have produced a better state, it's simply not considered. This is a deliberate simplification; explicit aspiration override (allowing tabu moves that beat the best) is straightforward to add later.

### Diversification

When `iter_since_improvement >= restart_after`:
1. Apply a random balanced perturbation: `diversification_pair_count` random (currently-red, currently-blue) edge pair flips.
2. Recompute `current_count` via `get_cliques_comprehensive` (the only full recount during a run).
3. Clear both tabu lists and the destroyed set.
4. Reset tenure to base, reset `iter_since_improvement = 0`.

Diversification is the natural place to refresh state, since we're already throwing away local context. It also caps the staleness of the destroyed set and the candidate-pool ranking.

### State Tracking: destroyed Set, Not CliqueCollection Update

`CliqueCollection` is a one-shot data structure populated from `set_cliques(all_cliques)` — there is no `add_clique` or `flip_edge` method. To work around this, tabu uses the same pattern as VDS: maintain a `HashSet<u32>` of original-clique indices that have been touched by any move in the current trajectory, used purely for filtering candidate-clique sampling. Newly-created cliques mid-trajectory are not tracked individually — but their count is correctly reflected in `current_count` because every move's delta is exact.

This is a deliberate trade: candidate sampling becomes increasingly approximate as the trajectory progresses, but the algorithm continues to make correct local decisions on what to flip. Diversification is the periodic reset that keeps approximate sampling from drifting too far.

### Result Submission

After the schedule completes, if the best graph found beats the current top-N threshold, it is submitted as a full graph bitstring via `add_sa_result_to_top_results()`. (The "SA" naming is a holdover; the underlying call accepts any worker mode that walks far from the base graph.) A bitstring submission is preferred over edge-flip lists because tabu may apply tens of thousands of mutations across a single run.

| `TABU_RANDOM_SEED` | -- | -- | Optional fixed seed for deterministic runs (tests only) |

Two notes on the log shape:

- The `SA:` prefix on the top-N submission line is a holdover from the SA worker's submission helper (shared call site `add_sa_result_to_top_results`). Not a bug, but misleading in tabu logs.
- The submission line fired on every run, including runs with `delta_from_initial=0` — i.e., tabu was unconditionally re-submitting the unchanged base graph back to the top-N sorted set. The submission gate doesn't currently check for actual improvement against the initial count. Worth fixing before any future re-run; flagged for whoever revives this worker.

Tabu emits only `Tabu starting` and `Tabu finished` per run, plus the top-N add line. This keeps log volume manageable across the fleet.

## Performance Characteristics

Per-iteration cost is dominated by `pool_size² × 2` edge-seeded Bron-Kerbosch calls (one pre-flip and one post-flip per pair eval). On the production graph (282 vertices, ~790K 8-cliques):

| `pool_size` | Pair evals/iter | BK calls/iter | Approx. ms/iter | Time per 50K-iter run |
|-------------|-----------------|---------------|------------------|------------------------|
| 5 | 25 | 50 | ~110 | ~9 min |
| 10 | 100 | 200 | ~400 | ~33 min |
| 20 | 400 | 800 | ~1700 | ~24 hr |

These figures come from the 2026-05-04 smoke test post-fix. The retirement run used `pool_size=10, max_iter=5000` and observed mean wall-clock of ~520 s/run (~8.7 min) — consistent with the table after accounting for the 5,000-iter (not 50,000-iter) budget. `pool_size=20` is unworkable on this graph (~24h/work-unit); `pool_size=10` is the practical ceiling. Smoke testing should use `pool_size=5` for fast iteration.

## Current Status — Retired

**Retired 2026-05-06.** A 4-worker A/B run from 2026-05-04 01:06Z to 2026-05-06 01:43Z (~48.5 hours) on the local `:tabu-test` image produced:

- 1,355 tabu runs started, 1,351 finished, ~6.75M total iterations, 6,755 diversification cycles
- **0 improvements**, 0 runs with negative `delta_from_initial`
- 0 panics, errors, or container restarts
- Mean wall-clock per run: ~520 s

Every completed trajectory ended with `delta_from_initial=0`. Across the run, the parallel 10-worker exhaustive fleet advanced campaign 2 from base count 789,974 → 788,544 (Δ −1,430 cliques across multiple stage transitions) — all progress was attributable to exhaustive; tabu contributed nothing.

Decision matched the investigation doc's pre-declared retirement branch: "0 improvements over 48+ hours → retire alongside VDS." The pre-run retune from `tenure=200` → `tenure=30` was the most defensible parameter change available based on smoke evidence, and it didn't change the outcome — at this graph density and with our balanced-pair move shape, narrow-trajectory tabu does not escape the local basin.

The compose service is now defined at `scale: 0`. Code (`src/tabu.rs`, `cycle_tabu_search`, env-var parsing) is left in place for any future re-run under a different move shape (e.g. 3- or 4-flip neighborhoods, single-edge flips on an unbalanced relaxation, or much wider candidate pools without clique-seed bias). Full retirement record and forecloses-vs-doesn't analysis: [`docs/investigations/retired-trajectory-methods.md`](../investigations/retired-trajectory-methods.md) (original investigation doc in git history).

### Known Issue for Future Re-Run

The top-N submission gate fires unconditionally, even when `best_count == initial_count` — see "Sample Log Output" above. This means every tabu run during the A/B re-pushed its unchanged base graph into the top-N sorted set. Worth fixing before any future re-run.
